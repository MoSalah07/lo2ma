# Lo2ma backend

> **Status: being built.** The app skeleton, its error handling, the database and the tooling are in place;
> the endpoints below arrive one feature at a time. Until then the web app runs against a mock of this
> service, and that mock defines the API described here.

The backend will serve the web and mobile apps, run the agent that picks meals, take payments, and send each day
of a weekly plan to the restaurant on time.

## Running it

You need [uv](https://docs.astral.sh/uv/) 0.13.1 and Docker. uv installs Python 3.14 and every package from
`uv.lock`, so nothing else is installed by hand. Copy `backend/.env.example` to `backend/.env` once. Then, from
the repo root:

| Command                                      | What it does                                                                  |
| -------------------------------------------- | ----------------------------------------------------------------------------- |
| `npm run dev:api`                            | starts the database, migrates it, then `fastapi dev` on http://localhost:8000 |
| `npm run check`                              | the whole repo, the backend included: pyright, ruff, pytest                   |
| `npm run test -w @lo2ma/backend`             | only the backend's tests (`typecheck`, `lint`, `format` work too)             |
| `npm run db:up` / `db:down`                  | starts or stops the local database                                            |
| `npm run db:migrate`                         | `alembic upgrade head` on the development database                            |
| `npm run db:seed`                            | loads the demo data from `seed/` (again any time: rows update in place)       |
| `npm run admin:create -- --email … --name …` | adds an admin: asks for a password, prints the authenticator link once        |

`backend/package.json` only runs these tools through `uv run --locked`, which fails when `uv.lock` is out of date.
Settings come from `LO2MA_*` environment variables or `backend/.env`. With `LO2MA_DEMO_SIGN_IN=true` (the
example's value, refused in production) the sign-ins follow the mock's demo rules: any six digits sign a
customer in except `000000`, and any `@lo2ma.test` email with a password of 8+ characters, then any code but
`000000`, signs an admin in. Outside production every sign-in code is also written to the log, since no SMS or
email provider is wired yet.

Python stays on 3.14 for now: 3.15 is out, but PyYAML has no 3.15 wheels yet, and `fastapi-cli` needs it.

The business rules come from `packages/core`, like the apps' own. `app/domain/rules.py` (the constants) and
`tests/vectors/*.json` (the TypeScript functions' answers) are generated by
`npm run export:python -w @lo2ma/core`. The Python versions of those functions live in `app/domain/` and are
tested against the vectors, so the server and the apps never disagree about a price, a time or a delivery area.

### The database

`compose.yaml` runs PostgreSQL 18.6 with PostGIS 3.6.4 and pgvector 0.8.7, built from `db/Dockerfile` with
exact package versions, on `127.0.0.1:5432`. It holds two databases: `lo2ma` for development and `lo2ma_test`
for the tests.

- Migrations are Alembic, configured in `pyproject.toml` (there is no `alembic.ini`). The URL comes from
  `LO2MA_DATABASE_URL`. New migration files are named by date and come out formatted by ruff.
- Every test run walks all migrations down and up again on `lo2ma_test`, and checks that the models match them.
  Each test runs in a transaction that is rolled back.
- The app talks to the database with SQLAlchemy 2 (async) on psycopg 3. psycopg's async mode can't use Windows'
  default event loop: `fastapi dev` and the tests are set up for it, and anything else that serves the app on
  Windows without `--reload` needs `--loop asyncio:SelectorEventLoop`.

## The API contract

The web app talks to `/api/*` only, and every response is validated by a zod schema in `packages/core`. The
mock handlers in `apps/web/src/mocks/handlers` answer those requests today, and `handlers.test.ts` pins their
behavior, so the FastAPI service has to return the same shapes, statuses and error codes.

Two checks keep the two sides together:

- **Shapes**: `npm run api:generate` writes this service's OpenAPI schema to `packages/api-client/openapi.json`, and
  openapi-typescript turns it into `src/schema.d.ts`. `packages/api-client/src/parity.ts` then asks the compiler
  whether each zod schema and the model of the same name describe the same JSON, so a field that is missing,
  optional on one side only, or of another type fails `npm run typecheck`. The tests fail while either generated
  file is out of date.
- **Behavior**: the backend's tests repeat the cases of `handlers.test.ts` against the real API, with the same
  statuses and error codes.

**Shared rules**

- Money is an integer number of piasters, everywhere.
- An error is a non-2xx status with a JSON body `{ "code": "…" }`. The apps turn the code into a message.
- The chat reply is a stream of server-sent events: `token` (words), `suggestions` (the meal cards, with the
  budget used), then `done`, or `error` with a code.
- A workplace is a point on the map (`lat`, `lng`), its name and district in both languages, and the user's notes
  for the courier. `PUT /prefs` refuses a point outside the service area (`SERVICE_AREA` in `packages/core`, Greater
  Cairo for now) with `422 outside_service_area`. Search should fold Arabic the way people type it (no diacritics,
  every alef alike, ى as ي, ة as ه); a real geocoder (Photon or Nominatim on OpenStreetMap) can stand behind
  `/places`.
- **The agent never confirms or pays.** It has no tool for either. Orders are created only by the user's own
  request to `POST /orders` or `POST /plan/confirm`.

**Customer endpoints**

| Method and path                          | Purpose                                                                             |
| ---------------------------------------- | ----------------------------------------------------------------------------------- |
| `POST /auth/otp`                         | send a one-time code to a phone number or an email                                  |
| `POST /auth/verify`                      | check the code and start a session                                                  |
| `GET /auth/session`                      | the signed-in user, if any                                                          |
| `POST /auth/sign-out`                    | end the session                                                                     |
| `GET /places/suggested`                  | popular workplaces, shown before anything is typed                                  |
| `GET /places/search?q=`                  | places whose name or district matches, in Arabic or English                         |
| `GET /places/reverse?lat=&lng=`          | what is at a map point (a building or a district), and whether Lo2ma delivers there |
| `GET /prefs`, `PUT /prefs`               | workplace, break time, budget, calorie limit, foods to avoid                        |
| `POST /chat`                             | a message to the agent; the reply streams back as server-sent events                |
| `POST /chat/transcribe`                  | multipart `audio` + `locale` → the words that were said                             |
| `GET /suggestions/:id`                   | one suggested meal with its dishes, bill and calories                               |
| `GET /suggestions/:id/nutrition`         | how each dish's calories were worked out: its foods, grams and protein              |
| `POST /suggestions/:id/nutrition/report` | the dish came different; queues it for review (`202`)                               |
| `GET /payment-methods`                   | the ways to pay                                                                     |
| `GET /orders`, `POST /orders`            | the user's orders; create one from a suggestion (the pay button)                    |
| `GET /orders/:id`                        | one order and its timeline                                                          |
| `GET /plan`                              | next week's plan, or the confirmed week with each day's status                      |
| `POST /plan/days/:date/swap`             | another meal for one day, before its cut-off                                        |
| `POST /plan/confirm`                     | confirm and pay the whole week                                                      |

**Admin endpoints** (a separate session: password, then an authenticator code)

| Method and path                                                        | Purpose                                             |
| ---------------------------------------------------------------------- | --------------------------------------------------- |
| `POST /admin/auth/sign-in`, `POST /admin/auth/verify`                  | the two sign-in steps                               |
| `GET /admin/auth/session`, `POST /admin/auth/sign-out`                 | the admin session                                   |
| `GET /admin/overview`                                                  | the numbers and charts for a day, a week or a month |
| `GET /admin/orders`, `GET /admin/orders/export`                        | orders with filters and paging, and the export      |
| `GET /admin/companies`                                                 | companies, for the order filters                    |
| `GET /admin/coupons`, `POST /admin/coupons`                            | list and create coupons                             |
| `GET /admin/agent/conversations`, `GET /admin/agent/conversations/:id` | the agent log: conversations and their steps        |

**Error codes the apps already handle**

`400` `invalid_request` · `invalid_message` · `invalid_prefs` · `invalid_order` · `invalid_code` ·
`invalid_audio` · `invalid_query` · `invalid_point` · `invalid_coupon` · `invalid_challenge` · `invalid_destination` ·
`unknown_company` · `ends_in_past` — `401` `auth_required` · `signed_out` · `admin_required` ·
`invalid_credentials` — `404` `not_found` · `not_onboarded` · `suggestion_not_found` · `order_not_found` ·
`plan_not_found` · `day_not_found` — `409` `day_locked` · `plan_expired` · `duplicate_code` —
`413` `audio_too_large` — `422` `no_speech` · `outside_service_area` — `500` `internal_error`, with nothing
about the error itself

A malformed request is never FastAPI's `422`: each route names its own code (such as `invalid_prefs`), and
`invalid_request` covers the rest. It is `400`, except the admin sign-in, where a malformed one is `401`
`invalid_credentials` like a wrong password. An unknown path is `404` `not_found`.

## The agent

- A tool-calling loop: the model reads the user's message and the saved preferences, then calls tools to search
  meals near the office, build each bill, and check the budget, the calorie limit and the minimum order
  (100 EGP of food before fees). It answers with three suggestions.
- It has no tool that confirms or pays, and the backend refuses to create an order from anything but the user's
  own request.
- Every step is logged, which is what the admin's agent log shows.
- An evaluation set of real-style requests in Egyptian Arabic and English decides which cloud model to use, and
  catches regressions when prompts or tools change.

## Weekly plans and scheduling

Each day of a confirmed week stores the moment its order must go out (`send_at`, 45 minutes before the planned
arrival). A tick every minute picks the orders that are due with `FOR UPDATE SKIP LOCKED`, so two workers never
send the same order. There is no queue service in the first version: PostgreSQL is enough. A restaurant refusing
or running late is handled per day, without touching the rest of the week.

## Payments

A payment sandbox first: the order is drafted, the user confirms and pays, and the provider's webhook settles it.
Every payment request carries an idempotency key, so a retry never charges twice. Coupons are checked against the
minimum order on the server too.

## Voice

- Dictation needs only `POST /chat/transcribe`. The speech-to-text model for Egyptian Arabic will be chosen by
  evaluation, like the language model. Until then the demo hears the mock's sentence in any recording
  (`seed/voice.json`), so the chat that follows finds the same meals.
- Real voice calls come later, with LiveKit Agents: speech-to-text, then the same agent loop, then Egyptian
  text-to-speech, with turn detection and interruptions. The web app's call screen is already built for it.

## Connecting the web app

Run the web app with `NEXT_PUBLIC_API_MOCKING=disabled` and it sends every `/api/*` request to the real service
instead of the in-browser mock: `next.config.ts` forwards them to `API_URL` (`http://127.0.0.1:8000` by default).
The browser only ever talks to the web app's origin, so the session cookie is first-party and there is no CORS.
Nothing else in the app changes.

Every route here lives under `/api`, so the path is the same in the browser, in the logs and in the tests.
`/health` (and, later, `/internal/*`) sits outside it, out of the web app's reach.

The demo data is the mock's own: places, foods, restaurants, dishes, companies and coupons. The web app writes it
to `backend/seed/*.json` (`npm run export:seed -w @lo2ma/web`), `npm run db:seed` loads it, and `npm run dev:api`
seeds before it starts. Implemented so far: `/places/*`, `/prefs`, `/auth/*`, `/chat/transcribe`,
`/suggestions/:id/nutrition` (and its report), `/payment-methods` (the mock's demo card and wallet until payments),
`/admin/auth/*`, `/admin/companies` and `/admin/coupons`, plus the menus behind the meal search. A suggestion's id
names its meal (`r01.m1.m4`: restaurant r01, dishes r01-m1 and r01-m4), so any meal opens from a link. A coupon's
status isn't stored: it has ended once its last day has passed in Cairo or its uses ran out, and only a pause is
kept. The mock's restaurants only say how far they are from the Smart Village, so the seed places each one that far
from it, in its own direction; workplaces elsewhere in Cairo have no demo restaurants nearby.
